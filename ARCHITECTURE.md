# Architecture

`wickra-backtest` is a streaming-native, event-driven backtester built on the
`wickra-core` indicator kernels. A strategy is **data** (a JSON spec), so the
same strategy runs identically in ten languages and a backtest matches a live
run by construction.

## Crates

| Crate | Role |
|-------|------|
| `wickra-backtest-core` | The engine: spec DSL, indicator registry, rule evaluation, portfolio accounting, execution model, metrics, report and the streaming/batch runners. |
| `wickra-backtest-data` | Data loaders (CSV / JSON / JSON Lines / Parquet) and transforms (resampling, Renko / Kagi / Point-and-Figure bars). |
| `wickra-backtest` | A thin facade re-exporting the public API. |
| `wickra-backtest-cli` | The `wkbt` command-line backtester. |
| `wickra-backtest-bench` | Criterion throughput benchmarks. |
| `bindings/*` | Python, Node.js, WASM, C ABI, C#, Go, Java and R language bindings. |

## Data flow

```
candles ──▶ StreamingBacktest::step(candle, feeds)
                 │
                 ├─ 1. fill any pending order (look-ahead-free: on this bar's open)
                 ├─ 2. update each registered indicator from a BarInput
                 │      (candle + optional reference / derivatives / order-book /
                 │       trade / cross-section feeds)
                 ├─ 3. evaluate intrabar stop-loss / take-profit / trailing /
                 │      liquidation along the conservative O→H→L→C path
                 ├─ 3b. charge perpetual funding to an open position
                 ├─ 4. mark-to-market and push an equity point
                 └─ 5. evaluate entry / exit / short rules → queue an order
                        (filled at step 1 of a later bar, after latency)
            finish() ──▶ close any open position ──▶ BacktestReport
```

The historical `run` / `run_with_capital` is exactly this loop fed from a slice;
pointing `step` at a live feed turns the same engine into the live bot. That
single code path is why a backtest equals a live run.

## Key design decisions

- **Look-ahead bias is structural.** A signal computed on a bar's close fills on
  the *next* bar's open by default; the optimistic same-bar `close` fill is
  explicit opt-in. The engine never reads a future bar.
- **The registry is generated.** `tools/gen_registry.py` parses the
  `wickra-core` indicator sources and emits `registry.rs`, so the 495
  backtestable indicators stay in lock-step with the library. Each is wrapped
  behind a uniform, object-safe `EvalIndicator` the engine drives from a
  `BarInput`.
- **Feeds are an extensible bundle.** `Feeds { reference, deriv, orderbook,
  trades, cross_section }` threads microstructure context to the indicators that
  need it; absent feeds are simply `None`. `run_json` marshals one JSON request
  (candles + spec + feeds) so every binding exposes the full surface without
  marshalling variable-length feed arrays across the FFI.
- **One kernel, ten languages.** Every binding calls the same engine and returns
  the same JSON report. The golden corpus (`golden/`) pins this byte-for-byte
  for the OHLCV path and all four microstructure feed families.

## What lives where — the navigation cheat sheet

| You want to … | Look in |
|---|---|
| add a condition or operand to the spec DSL | `crates/wickra-backtest-core/src/rules.rs` and `spec.rs`. Anything that can look back must also teach `condition_lookback` / `operand_lookback`, or the bounded history ring will be too short for it |
| change the strategy spec's shape | `spec.rs`, then rebless `schema/strategy_spec.schema.json` — a test fails on drift, so the change shows up in the diff rather than in someone's parser |
| change what the report contains | `report.rs` and `metrics.rs`. Every binding returns this JSON, so the golden corpus has to be reblessed and every binding's golden test re-run |
| change how an order fills | `engine.rs` — the intrabar `O → H → L → C` path and the pending-order queue — and `portfolio.rs` for the accounting |
| add an indicator | nowhere here. `registry.rs` is generated by `tools/gen_registry.py` from the `wickra-core` sources; add it upstream and regenerate |
| add a loader, a resampler or a bar type | `crates/wickra-backtest-data/src/lib.rs` |
| add a CLI subcommand | `crates/wickra-backtest-cli/src/main.rs` |
| expose a new export to every language | `bindings/c/src/lib.rs` first — it is the hub six languages go through — then the cbindgen header, its vendored copy under `bindings/go/include`, and each binding. `scripts/check_binding_surface.py` will tell you which ones you missed |
| add a fuzz target | `fuzz/fuzz_targets/<name>.rs`, registered in `fuzz/Cargo.toml` (its own workspace) |
| change the CI matrix | `.github/workflows/ci.yml` |
| change the release pipeline | `.github/workflows/release.yml`. A `v*` tag publishes to six registries in one irreversible run — rehearse on a throwaway tag. The publish jobs are independent, so one failing leaves the rest published |

## What is **deliberately** not in this repo

- **Order routing and execution.** The engine computes; it opens no sockets,
  places no orders and holds no keys. The streaming API is the seam where a live
  bot attaches, and that bot is the caller's.
- **Indicators.** They live in `wickra-core`. This repository wraps 495 of them
  behind one object-safe interface and never reimplements one, which is what
  keeps a backtested value identical to a live one.
- **Parameter search.** Optimisation, walk-forward and cross-validation are
  loops *around* a backtest. The engine is the inner loop and is deliberately
  cheap to call many times; the search is not its job.
- **Portfolio construction across strategies.** One spec, one symbol, one
  account. Allocating between several is a layer above this one.
- **Charting.** No plotting code ships in any published package.
- **Exchange aggregation.** The data crate reads files and resamples them. A
  general exchange abstraction is `ccxt`'s job, not this one's.

## Performance characteristics

The engine is O(1) per bar: cost depends on the strategy, never on how many bars
have already been processed. Two things make that true and are worth knowing
before changing either.

- **History is bounded.** The engine keeps a ring of past bars sized by the
  deepest lookback the spec actually references (`history_depth`), not by the
  run. A rule that reaches further back than it declares will read a bar that is
  no longer there.
- **Equity is not bounded.** The curve accumulates one point per bar, because a
  report has to be able to describe the whole run. A long live session should
  read `latest_equity` each bar and persist it, then end the session with
  `finish`.

Where the numbers are: `crates/wickra-backtest-bench` for the engine under
criterion, `bindings/<lang>/benchmarks/` for what each language's boundary costs,
and [BENCHMARKS.md](BENCHMARKS.md) for the measured results and the comparison
against other libraries.

## Trust boundaries

The engine is pure computation: no network, no order placement, no API keys.
Inputs (specs, candles, feeds) are untrusted JSON; parsing and evaluation never
panic (see `tests/properties.rs`), always returning a `Result`. See
[THREAT_MODEL.md](THREAT_MODEL.md).

## Stability commitments

- **MSRV.** Workspace: Rust 1.86. The Node binding: 1.88, which NAPI-RS pins.
- **Pre-1.0.** The strategy spec and the report schema may change between minor
  versions, and `GOVERNANCE.md` says so. What follows describes how a change is
  made visible, not a promise that none will happen.
- **The strategy spec is the public contract**, more than any Rust signature is:
  it is what a caller writes, in every language. `schema/strategy_spec.schema.json`
  is committed and a test fails when the generated schema drifts from it, so a
  change to the spec cannot land without appearing in the diff.
- **The report.** Adding a field is non-breaking: every binding hands back JSON
  and the consumers parse it. Removing or renaming one is breaking, and the
  golden corpus turns it into a failing test in ten languages at once rather than
  a surprise for a caller.
- **The C ABI.** Six of the ten reaches go through `bindings/c`. A changed
  signature there is breaking for all six simultaneously, so it is a
  major-version event; adding an export is not.
- **Indicator availability.** The registry is generated from `wickra-core`, so
  what this engine can reference is decided upstream. An indicator that
  disappears there disappears here, and the registry's own count test fails
  loudly rather than silently shrinking the surface.

## Known sharp edges

Written down so nobody spends an afternoon rediscovering them.

- **`registry.rs` is generated.** Three and a half thousand lines of it. Edit
  `tools/gen_registry.py` and regenerate; a hand edit is lost on the next run.
- **The C header exists twice.** `bindings/c/include/wickra_backtest.h` is
  generated by cbindgen, and `bindings/go/include/wickra_backtest.h` is a
  committed copy because the parent directory is outside the Go module. CI
  diffs them; both have to move together.
- **`finish` consumes the stream handle** in every binding, and `free` does not.
  In C this asymmetry is a double free if you get it wrong, which is why the C++
  wrapper expresses the two as different operations.
- **The engine's tests are the anchor for the corpus.** `golden/expected/` is
  written by the Rust golden test in bless mode; the other nine languages only
  compare against it. Reblessing without re-running them proves nothing.
- **The fuzz crate detaches itself from the workspace** so cargo-fuzz can build
  it with sanitiser flags. That also puts it outside `cargo deny` and outside a
  plain `cargo test --workspace`; it has its own Dependabot entry for the same
  reason.
